## Context and Problem Statement

Mesh v3 (ADR-0016) embeds iroh in three Go programs: the fly hub, the
Talos system extension (node agent) and the desktop daemon. iroh is a
Rust library; n0 ships first-party uniffi bindings for Python, Swift,
Kotlin and Node — **not Go**. The only Go binding is community-
maintained (`git.coopcloud.tech/decentral1se/iroh-go`), pinned one
patch behind core and owned by one person. Probe P0.4 (`359.1.4`)
passed the API-churn kill criterion **with the condition** that we
own the Go binding rather than take that community package as an
unforked load-bearing dependency. This ADR settles *how* we own it.

## Decision Drivers

- **Three embeddings move together.** One binding, regenerated once
  per iroh bump, keeps the P0.4 estimate (~1 engineer-day per
  quarterly bump) honest; two mechanisms (binding here, sidecar there)
  would double it.
- **Reproducible from the flake** (invariant 2, "servers derive"): the
  binding must be a pure function of pinned upstream sources — no
  hand-edited generated code, no network at build time.
- **No dependency on a single volunteer** (P0.4 condition).
- **The protocol module stays transport-free** (ADR-0020,
  `protocol/docs/desired-state/invariants.md`): whatever we pick lives
  outside `protocol/`.
- **The Talos extension is the hardest link target** (static, no
  glibc assumptions); the choice must not foreclose it.
- Evidence over preference: the task was time-boxed with an explicit
  "sidecar instead" as a valid outcome.

## Considered Options

### Option A: In-house uniffi-bindgen-go off iroh-ffi (chosen)

Build `iroh-ffi` (n0's first-party uniffi crate) as a static/shared
library in the flake, run `uniffi-bindgen-go` (NordSecurity) over it,
apply any fixups as an idempotent script, check the generated package
in and **drift-check** it against a fresh generation on every build.

- Pros: same process, same address space, ordinary Go API; one pipeline
  for all three embeddings; the ffi crate is first-party and tracks
  core; measured: generates and compiles with **three exact-match
  textual fixups, no generator fork**; async, foreign-implementable
  traits (`ProtocolHandler`), errors, records all work; direct and
  custom-relay smokes pass on aarch64-darwin and aarch64-linux; a core
  1.0.2→1.1.0 bump regenerated a byte-identical package.
- Cons: **cgo everywhere** — Go's free cross-compilation is gone, one
  builder per (os, arch); 15–16 MB binaries; `uniffi-bindgen-go` is
  itself single-vendor and lags uniffi minors (mitigated: pinned, and
  a uniffi bump is the moment to re-check the fixups); generated API
  has warts (`Option<Arc<T>>` → `**T`, blocking async calls); cold
  builds are slow (bindgen ~45 min once, iroh-ffi ~10 min).

### Option B: Rust sidecar process

A small Rust binary embedding iroh directly, driven from Go over a
unix socket / stdio protocol we design.

- Pros: Go stays pure (cross-compile intact, no cgo); direct use of
  the Rust API with no binding-generator dependency; the Talos
  extension could ship the sidecar as a second static binary.
- Cons: a process boundary and a bespoke IPC protocol of our own to
  version, secure and debug — for every stream, on the hot path; two
  binaries to supervise in every embedding (three supervision stories
  for three embeddings); the IPC surface would re-implement a subset
  of the iroh API by hand, i.e. the maintenance cost P0.4 wanted to
  avoid, in a form no generator helps with. Not built: bindgen
  succeeded well inside the time-box, so no data justified it.

### Option C: Community `iroh-go`, forked

Fork `decentral1se/iroh-go` and maintain the fork.

- Pros: zero-day start.
- Cons: it *is* Option A's output, generated by someone else on their
  schedule with their fixups; forking inherits the generated code
  without the pipeline that produced it. Ruled out by P0.4's condition
  and subsumed by A (we get the pipeline, not just the output).

### Option D: Wait for first-party Go bindings from n0

- Cons: no signal n0 plans them; blocks Phase 1 indefinitely. Ruled
  out.

## Decision Outcome

Chosen: **Option A**, because the evidence removed its main risk (a
brittle generator) — three textual fixups and no fork — while the
sidecar's costs (IPC design, process supervision ×3, hand-maintained
API subset) are structural and permanent. The pipeline lives in
`iroh-go/` (own `go.mod`, own nix directory), exposed as
`packages.{iroh-go,iroh-go-smoke,iroh-ffi,iroh-ffi-static,iroh-relay,
uniffi-bindgen-go}` and `apps.iroh-go-regen`; the checked-in
generated package is drift-checked on every `nix build .#iroh-go`.
Pins: iroh-ffi **1.1.0**, uniffi-bindgen-go **0.7.1+v0.31.0**,
iroh-relay **1.1.0**. The ffi crate's own lock pins core iroh 1.0.2;
bumping it to 1.1.0 is tested green and tracked as `htt`.

### Consequences

- Easier: one regen procedure for all Go embeddings; every iroh bump
  is `sources.nix` pins → `nix run .#iroh-go-regen` → smoke.
- Harder: **cgo is now a fact of every Go binary that talks to the
  mesh.** Cross-compilation needs a nix builder per target
  (`pkgsCross`); the config-server image build and the Talos extension
  packaging must account for it. The hub's fly image is x86_64-linux —
  **unverified** until `g3u` runs the smoke on an x86_64 builder.
- The Talos system extension needs a fully static (musl) link of Rust
  archive + cgo Go; the `pkgsStatic` path is identified, not attempted.
  This is the risk most likely to reopen Option B for that one
  embedding.
- `protocol/` remains free of iroh; only consumers (hub, agent,
  desktop) import `iroh-go/iroh`.
- A thin idiomatic wrapper over the generated API is deferred until the
  first real consumer shows which warts matter.

### Confirmation

- `g3u`: `nix build .#iroh-go-smoke` green on `ubuntu-latest`
  (x86_64-linux) in CI.
- Phase 1 (`359.8.*`): the hub links the binding and serves one ALPN
  stream in production shape; `359.1.3`: the Talos extension links it
  statically. If the static link proves impossible after honest
  effort, revisit Option B **for the extension only** and record it as
  an amendment here.
- Two consecutive iroh bumps each cost ≤ ½ day for the Go side (the
  P0.4 kill threshold, restated for the binding).
- Invalidated if n0 ships first-party Go bindings (then evaluate
  switching the pipeline's generator, keeping the drift check), or if
  uniffi-bindgen-go stops tracking uniffi and the fixup list grows
  beyond textual edits.
